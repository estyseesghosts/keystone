# Security audit — Keystone v2 (2026-10-25)

Scope: auth (OAuth/PKCE, MiAuth), token storage, cross-origin handling, deep links, link/HTML/MFM rendering, instance-URL handling, dependencies, secrets, native config. No source modified. Only issues verified in code are listed.

## Summary

The core design is strong: tokens are bound to a session/origin at the transport layer, absolute URLs are same-origin-checked before any request, content is parsed to an allow-listed AST with a vetted-URL gate, and no `innerHTML`/`eval`/WebView exists. No secrets are committed. The real weaknesses are at the edges: tokens duplicated in plaintext MMKV (with Android `allowBackup=true`), HTTP redirects followed with Misskey tokens in the POST body, an unvetted `Linking.openURL` in chat attachments, release builds signed with the debug keystore, and a custom-scheme MiAuth callback.

No critical findings. 1 high, 5 medium, 4 low.

## Findings

### H1 (high) Android release build signed with the debug keystore
- `android/app/build.gradle:100-115` (release `signingConfig signingConfigs.debug`, `storePassword 'android'`).
- Scenario: any release/side-loaded APK is signed by a publicly known key. Anyone can build a same-signature update/impersonating app. Combined with the `keystone://` scheme (M3), signature-based trust does not exist.
- Fix: dedicated release keystore supplied via CI secrets / gradle properties; fail the release build when absent. Note `android/` is generated by prebuild (`app.config.js`), so fix in a config plugin.

### M1 (medium) Session tokens duplicated in plaintext MMKV; the SecureStore vault is only a second copy
- `src/state/session/store.ts:30-36, 428-438`; `src/storage/mmkv.ts:51` (`new MMKV({id: 'keystone'})`, no `encryptionKey`); `src/storage/tokens.ts:39-41` (falls back silently to envelope copy).
- The envelope `keystone_sessions` holds the bearer token on disk, unencrypted, on every platform; the Keychain/Keystore vault therefore adds no protection. Mastodon `client_secret`s (`packages/fedi/src/mastodon/oauth.ts:297-340`) are in the same store.
- Scenario: device backup extraction, rooted/jailbroken device, or file-level read gives full account tokens (Misskey tokens carry write:* and admin read scopes).
- Fix: keep only non-secret metadata in the envelope and read tokens from the vault only (async hydrate before first request), or at minimum give MMKV an encryptionKey stored in SecureStore.

### M2 (medium) Android `allowBackup="true"` exposes the token store
- `android/app/src/main/AndroidManifest.xml:15`.
- Amplifies M1: `adb backup` / cloud backup carries the MMKV file (tokens, persisted query cache incl. DMs).
- Fix: `android:allowBackup="false"` (expo `android.allowBackup: false` in `app.config.js`) or exclude MMKV via data-extraction rules.

### M3 (medium) Misskey MiAuth callback uses a custom scheme with no binding secret
- `src/screens/Login.tsx:78-95` (`Linking.createURL` -> `keystone://`), `src/screens/AuthCallback.tsx:49-67`, manifest intent filter lines 25-31 (`keystone`, `exp+keystone`, BROWSABLE, no autoVerify).
- On Android another app can register `keystone://` and receive the redirect `?session=<uuid>`. MiAuth `miauth/<session>/check` needs no other secret, so the interceptor can redeem the approved token. (Mastodon is protected by PKCE; MiAuth has no equivalent.) Session ids on the fallback path use `Date.now()+Math.random()` (`packages/fedi/src/misskey/external.ts:127-130`, `auth.ts:66-71`), weak if `crypto.randomUUID` is absent on Hermes.
- Fix: use https App Links / Universal Links for the callback, and fail closed (no Math.random fallback) when no CSPRNG exists.

### M4 (medium) Misskey token sent in POST body; fetch follows redirects by default
- `packages/fedi/src/misskey/client.ts:200` (`i: params.i ?? session.token` in JSON body); `packages/fedi/src/core/http.ts:~232` fetch call with no `redirect:` option (grep for `redirect:` in packages/fedi/src finds nothing).
- The same-origin check applies only to the initial URL. A malicious or compromised instance (or an HTTP-to-other-host proxy) answering 307/308 makes fetch re-POST the body, token included, to another origin. (Header-based tokens are stripped cross-origin by fetch; body tokens are not.) Same for `postDirect` in `external.ts:~165` and the native sign-in path with username/password.
- Fix: `redirect: 'manual'` (treat 3xx as error) or `'error'`, or re-validate `response.url` origin; consider sending the token via `Authorization: Bearer` (Misskey supports it).

### M5 (medium) Unvetted URL passed to `Linking.openURL` (chat attachment)
- `src/screens/ChatThread.tsx:51` (`Linking.openURL(file.url as string)`), `file.url` comes from server JSON via the Misskey chat adapter (no `safeHttpUrl`; other call sites such as `NewsTab.tsx:32` do gate).
- Scenario: a remote chat sender (federated/malicious server field) supplies `tel:`, `sms:`, `intent://`, `file:` or custom-scheme URLs; one tap launches arbitrary handlers. On web, `javascript:` via `Linking.openURL` -> `window.open` can execute in the app origin (XSS with access to MMKV-in-localStorage tokens, see L1).
- Fix: wrap with `safeHttpUrl` in the adapter or at the call site.

### L1 (low) Web build stores tokens in localStorage-backed MMKV
- `src/storage/tokens.web.ts:3-6`, acknowledged "dev-grade". Any XSS (see M5) exfiltrates all sessions' tokens. Document as release blocker for web or move to in-memory + httpOnly proxy; add CSP at the host.

### L2 (low) `openExternal` allows `mailto:` and hrefs are not rechecked
- `src/components/richtext/mentionRouting.ts:15-18`; `packages/fedi/src/core/content/ast.ts:286-333`. AST hrefs are vetted (http/https/mailto, no credentials), so this is safe today; but `openExternal` itself accepts any string and exports as a public helper. Add `safeUrl` inside `openExternal` as defence in depth. Also `showToast(String(e))` may echo URL content.

### L3 (low) `http://` instance origins accepted for any host; PKCE/state fall back to Math.random
- `packages/fedi/src/core/http.ts` `normalizeOrigin` ("local test targets only" comment, not enforced); `packages/fedi/src/misskey/external.ts` scheme handling; `packages/fedi/src/mastodon/oauth.ts:446-449` (`randomToken` falls back to `Math.random` for PKCE verifier/state when `crypto.getRandomValues` is missing). iOS ATS has `NSAllowsArbitraryLoads=false` (good), but Android has no `usesCleartextTraffic=false`/network security config, so cleartext logins/tokens are possible for any host a user types.
- Fix: restrict http to localhost/private ranges in release builds; throw instead of falling back to `Math.random`.

### L4 (low) Persisted query cache holds private data, plaintext
- `src/state/queries/Provider.tsx:63-80` persists all queries (24h) to MMKV with no dehydrate filter; includes conversations/notifications (`src/state/queries/conversations.ts`, `chat.ts`). Keys are session-scoped, but data is unencrypted and survives until expiry; verify it is purged on sign-out. Add `shouldDehydrateQuery` exclusions for DMs/chat.

## Looked solid
- Transport: `requestJson` has no token parameter, rejects cross-origin absolute URLs and non-`/` paths before I/O, `credentials: 'omit'` (`packages/fedi/src/core/http.ts`). Nodeinfo follow-links are same-origin only (`detect.ts:741-746`).
- Content: HTML via htmlparser2 and MFM via mfm-js to a single AST; `safeUrl` allows only http/https/mailto, strips credentials, rejects relative/protocol-relative/`javascript:`/`data:` (`core/content/ast.ts:286-333`); image URLs restricted to http(s). No `innerHTML`, `dangerouslySetInnerHTML`, `eval`, `new Function`, WebView or `javascript:` sinks in `src/` or `packages/` (grep verified).
- OAuth: PKCE + state, pending flow read-and-delete (replay guard), origin taken from the pending row not the URL, `?code` cleared from the web URL, token verified before store (`AuthCallback.tsx`, `MastodonCallback.ts`, `LoginFlows.ts`). MiAuth requests least-privilege per-endpoint scopes; native credential kept in memory only.
- Logging: only two `console` calls in app code (`Conversation.tsx:104`, `PostPoll.tsx:134`), neither logs tokens; `HttpError.path` documented token-free; oauth.ts forbids logging secrets.
- Secrets/config: no keys/secrets tracked (grep); `.gitignore` covers `.env*`, keystores; Apple team ID is non-secret; config plugins are benign; iOS ATS strict (local networking only); Android permissions minimal (INTERNET, storage<=32, RECORD_AUDIO, VIBRATE; SYSTEM_ALERT_WINDOW is present, likely dev-client only — confirm it is removed in release).
- Dependencies: small set, all semver/Expo-pinned, lockfile present (`pnpm-lock.yaml`); no postinstall oddities seen. Did not run `pnpm audit` (not verified).
