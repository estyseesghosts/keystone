# P6.1 — Avatar and banner upload

Plan ref: `docs/clickstone.md` §1.8 (Wave 1 — parity)
Status: done
Branch: `p6.1-avatar-banner`

## Goal

`ProfileEditor` no longer disables avatar/banner with
`errors.unsupported.avatar`: both families upload for real through one
honest `Backend` seam (`uploadProfileImage(kind, file)`), Mastodon as the
credential multipart `PATCH` (`avatar`/`header`), Misskey as a Drive
upload plus `i/update` (`avatarId`/`bannerId`), with on-pick upload,
row-level progress/errors, and a cache refresh of the viewer account.

## Steps

- [x] 1. `Backend.uploadProfileImage?(kind: "avatar" | "banner", file: File):
      Promise<Account>` added (optional member; absent ⇒ UI disables with a
      reason). `ProfileImageKind` exported from core.
- [x] 2. Mastodon transport seam: `MastoClient.patchFormData` (multipart
      PATCH, boundary left to fetch) + `guarded()` pass-through +
      `api/client.ts` facade.
- [x] 3. `mastodon/endpoints.updateCredentialImage`: one `FormData` key
      (`avatar` or `header`), `PATCH /api/v1/accounts/update_credentials`,
      credential-account shape check.
- [x] 4. Mastodon backend implements `uploadProfileImage` →
      `adaptCredentialAccount`. `updateProfile` now refuses a Drive-shaped
      `avatarId`/`bannerId` as an unknown field
      (`errors.unsupported.profileField`) instead of claiming the family
      cannot change images at all.
- [x] 5. Misskey backend implements `uploadProfileImage`: `drive/files/create`
      (root) via the existing transport `upload`, then `i/update` with the
      returned id. `updateProfile` already accepted the ids.
- [x] 6. `src/components/Profile/pickProfileImage.ts`: images-only picker
      with an explicit permission request; typed outcome
      `picked | cancelled | denied`.
- [x] 7. `EditorImageRow` component (preview, choose/replace button,
      `Uploading…`, per-row error, disabled-with-reason).
- [x] 8. `ProfileEditor` wires both rows: upload on pick (no save
      round-trip), local preview then the server URL, one upload at a time,
      honest permission/validation messages, text fields untouched, and
      `setQueryData(me)` + `invalidateQueries(account)` after success.
- [x] 9. Tests: new `packages/fedi/test/profile-images.test.ts` (Mastodon
      multipart field names, Misskey upload→id order, both families expose
      the member); ProfileEditor tests for enable/progress/error/denied/
      cancel/cache-refresh/unavailable; w8 MD6 id-refusal updated.
- [x] 10. Verify: typecheck + lint + full test trio.

## Acceptance

- [x] Mastodon request is a multipart PATCH whose only file field is
      `avatar` (or `header`) — asserted on the `FormData` object, no JSON
      body anywhere.
- [x] Misskey order pinned: `drive/files/create` then `i/update` with
      `{avatarId}` / `{bannerId}` equal to the returned Drive file id.
- [x] `ProfileEditor` rows are enabled controls on both families; pressing
      one calls `uploadProfileImage('avatar'|'banner', file)` and neither
      `updateProfile` nor `goBack`.
- [x] Progress (`Uploading…`), a failed upload (server message, preview
      rolled back) and denied photo permission all render on the row.
- [x] A backend without the member keeps both rows visible, disabled, with
      the reason.
- [x] Existing profile save/fields/overlay tests unchanged and green.
- [x] `npx --yes pnpm@12.14.0 typecheck && … lint && … test` green
      (167 suites / 2103 tests).
