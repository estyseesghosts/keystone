# P6.0 — Translation gate uses the right flag

Plan ref: `docs/clickstone.md` §0.4 (Wave 0)
Status: done
Branch: `p6.0-translate-gate`

## Goal

Make `capabilities.translation` family-scoped: Mastodon-family reads
`configuration.translation.enabled` (v1/v2 instance body; Akkoma keeps
`akkoma:machine_translation`), Misskey-family reads `meta.translatorAvailable`.
One family's evidence must never decide the other family's flag.

## Steps

- [x] 1. Audit every path that builds/sets `capabilities.translation`.
      One real leak: `buildCapabilities` applied `translatorAvailable` and
      `translationAdvertised` regardless of flavor, so stored session
      evidence of the wrong family could flip the flag on
      `backendForSession` / `activeBackend`.
- [x] 2. Scope the evidence in `buildCapabilities` with `familyOf(flavor)`:
      `translatorAvailable` → Misskey family only;
      `translationAdvertised` → Mastodon family only;
      `akkoma:machine_translation` → Mastodon family only; undetected
      flavor ignores all three and stays `unknown`.
- [x] 3. Keep `mastodon/instance.ts` `buildFeatures` on
      `configuration.translation.enabled` (v1+v2). It is a
      Mastodon-family-only module, so the config can never be read for a
      Misskey body; fenced with a test that an alien
      `translatorAvailable` in an instance body is ignored.
- [x] 4. Keep `createTranslator` family-scoped (Misskey probes `meta`,
      Mastodon uses the capability table and never probes `meta`); fenced
      with tests.
- [x] 5. Menu/card gates unchanged: both read only
      `capabilities.translation` (`supported` enables; `unknown` /
      `unsupported` stay disabled with the existing reasons). No new
      screen, no new string.
- [x] 6. Tests: cross-family fence per family (`detect.test.ts`), session
      evidence seam (`session-evidence.test.ts`), Mastodon adapter
      (`mastodon-instance.test.ts`), translator (`misskey-translate.test.ts`).
