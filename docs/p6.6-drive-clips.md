## 1. Target

Two screens with the same structure, components and controls:

| | My Uploads (`/drive`) | Clips (`/clips`) |
|---|---|---|
| Items | folders + files | Favourites folder (pinned) + clips |
| Thumbnail | file preview, or a type icon | mosaic of up to 4 photos |
| Views | grid / list (toggle, remembered) | grid / list (toggle, remembered) |
| Open item | folder → navigate; file → detail panel | clip → clip screen |
| Create | New folder, Upload | New clip |
| Selection + bulk | yes (move, delete, sensitive) | no (non-goal) |
| Drag and drop (web) | OS files → upload; items → folder/breadcrumb = move | no |

The Drive screen should behave like a cloud storage client: breadcrumbs, nested folders, multi-select, upload queue with progress, drag and drop, delete, a storage usage bar.

### Favourites live in the Clips UI (Keystone presentation only)

On the server, Misskey favourites and clips are **separate features**: favourites are `i/favorites` + `notes/favorites/create|delete`; clips are `clips/*`. Keystone keeps them separate in the data layer and in the cache. Favourites are **never** modelled as a clip, never sent to a `clips/*` endpoint, and never counted against `clipLimit`.

What Keystone changes is the **UI**: the Clips screen shows Favourites as a **persistent folder** at the start of the grid/list, next to the user's clips.

- The Favourites folder uses the same tile/row, mosaic and header components as a clip, so the screen looks uniform.
- It is always present, cannot be renamed, deleted or made public, and shows no "n / limit" count.
- Opening it goes to the existing `Favorites` route (data: `BookmarksApi`, `bookmarks` feed descriptor). That screen is restyled with the same header layout as the Clip screen.
- On Misskey sessions there is no other Favourites entry point (no sidebar item, no button). The Clips screen is the way in.
- In "Add to clip" picker mode, the Favourites folder is the first target; choosing it calls `bookmarks.add`, not `clips.addNote`.

On Mastodon-family servers there are no clips. Bookmarks keep their own sidebar entry and screen; nothing changes there.

Misskey also has **clip favourites** (`clips/favorite`, `clips/my-favorites`: starring someone else's clip). That is a third, unrelated feature. It is out of scope for this plan (§7, O2), and the UI never calls it "favourites".

## 2. Server facts (verified upstream; cite this, do not re-derive)

### Drive

| Endpoint | Kind | Params | Notes |
|---|---|---|---|
| `drive` | `read:drive` | — | `{capacity, usage}` bytes |
| `drive/files` | `read:drive` | `limit ≤100, sinceId, untilId, folderId (null=root), type, sort` | `sort ∈ +createdAt,-createdAt,+name,-name,+size,-size` — **newer upstream; may be absent on Sharkey/older Misskey** |
| `drive/folders` | `read:drive` | `limit ≤100, sinceId, untilId, folderId` (parent; null=root) | Keystone currently calls it with no params → root only, 10 items |
| `drive/folders/show` | `read:drive` | `folderId` | packs with `detail: true` (parent chain, counts) → breadcrumbs |
| `drive/files/create` | `write:drive`, 120/h | multipart; `folderId, name, comment, isSensitive, force` | errors `INVALID_FILE_NAME`, `INAPPROPRIATE`, `NO_FREE_SPACE`, `MAX_FILE_SIZE_EXCEEDED`, `UNALLOWED_FILE_TYPE` |
| `drive/files/update` | `write:drive` | `fileId, name, folderId, isSensitive, comment` | |
| `drive/files/move-bulk` | `write:drive` | `fileIds (1–100, unique), folderId` | **newer upstream; may 404** → fall back to per-file `update` |
| `drive/files/delete` | `write:drive` | `fileId` | no bulk delete endpoint exists |
| `drive/folders/create` | `write:drive` | `name, parentId` | |
| `drive/folders/update` | `write:drive` | `folderId, name ≤200, parentId` | `NO_SUCH_PARENT_FOLDER`, `RECURSIVE_NESTING` |
| `drive/folders/delete` | `write:drive` | `folderId` | **`HAS_CHILD_FILES_OR_FOLDERS` if not empty** |

Role policy `driveCapacityMb` comes in the `i` response `policies`.

### Clips

| Endpoint | Kind | Params | Notes |
|---|---|---|---|
| `clips/list` | `read:account` | `limit ≤100 (default 10), sinceId, untilId` | own clips only |
| `clips/show` | `read:account` | `clipId` | |
| `clips/notes` | `read:account` | `clipId, limit ≤100, sinceId, untilId, search` | **ordered by note id (note creation time), not by when it was clipped** |
| `clips/create` / `update` / `delete` | `write:account` | `name 1–100, isPublic, description ≤2048` | |
| `clips/update` | `write:account` | `clipId` + optional fields | **server does `description \|\| null`: omitting `description` wipes it** |
| `clips/add-note` / `remove-note` | `write:account` | `clipId, noteId` | `ALREADY_CLIPPED`, `TOO_MANY_CLIP_NOTES` |
| `clips/favorite` / `unfavorite` / `my-favorites` | `*:clip-favorite` | `clipId` | starring other users' clips. **Out of scope** (§7) |

### Favourites (separate Misskey feature, shown inside the Clips UI)

| Endpoint | Kind | Params | Notes |
|---|---|---|---|
| `i/favorites` | `read:favorites` | `limit, sinceId, untilId` | rows `{id, note}`, ordered by favourite id = time favourited. Already wired: `BookmarksApi.list` |
| `notes/favorites/create` / `delete` | `write:favorites` | `noteId` | Already wired: `BookmarksApi.add/remove` |

Packed clip: `id, createdAt, lastClippedAt, userId, user, name, description, isPublic, favoritedCount, isFavorited?, notesCount?` (`notesCount` **owner only**).
Role policies: `clipLimit` (default 10), `noteEachClipsLimit` (default 200).

### Bugs found in current Keystone

- **B1** `Clips.tsx:366` rename calls `clips.update(id, {name, isPublic})` without `description` → stock Misskey wipes the description.
- **B2** `DriveFoldersApi.list()` sends no params → only the first 10 root folders; nested folders are unreachable.
- **B3** `clips.list()` sends `limit: 100` with no paging → a user with >100 clips (raised `clipLimit`) loses the rest.
- **B4** Clip scopes: Keystone requests `read:clips`/`write:clips`, which no upstream clip endpoint declares (they use `read:account`/`write:account`, already requested). Harmless; record it, do not change scopes in this plan.

## 3. Decisions made in this plan

| ID | Decision | Reason |
|---|---|---|
| DC-1 | One shared collection kit (`src/components/Collection/*`) renders both screens. | Consistency is the requirement; two hand-built screens drift. |
| DC-2 | View mode (`grid`/`list`) persists per screen, per device (MMKV device scope). Default `grid`. | Matches cloud-storage clients. |
| DC-3 | Favourites stay a separate data source (`BookmarksApi`, `bookmarks` descriptor, own query keys). The Clips screen renders a pinned Favourites folder item built from it; opening it navigates to the `Favorites` route. No reserved clip id, no `ClipSummary` for favourites. | Owner requirement (§1); Misskey keeps them separate server-side. |
| DC-4 | Clip mosaic = up to 4 images from the clip's notes in **server order** (newest note first). Favourites mosaic = newest favourited first. | `clips/notes` exposes no add order (§2). See O1. |
| DC-5 | Mosaic data loads lazily per visible tile, max 3 concurrent, cached 10 min, invalidated on add/remove note. | One `clips/notes` call per clip. |
| DC-6 | `clips.update` always sends `name`, `isPublic` and `description` (current values for unchanged fields). | B1. |
| DC-7 | `sort` and `move-bulk` are **probed** once per origin and cached (the `like.ts` pattern). Never sent when unsupported. | Sharkey 400s unknown params; older servers 404 the endpoint. |
| DC-8 | Bulk delete = parallel `drive/files/delete`, concurrency 4, with a per-item result report. No silent partial failure. | No bulk endpoint. |
| DC-9 | Deleting a non-empty folder: confirm dialog shows file + subfolder counts, then deletes depth-first. Abort and report if the walk finds >1000 items. | Cloud-storage expectation; the server refuses non-empty deletes. See O3. |
| DC-10 | Drive deletes are permanent (no server trash). Every delete is confirmed with item count and names (first 5). | |
| DC-11 | Drag and drop is web only. Native gets the same actions through selection mode + "Move to…" dialog. | RN has no cross-platform DnD; web has HTML5 DnD. |
| DC-12 | Sensitive files show a blurhash/blurred thumbnail with a "Sensitive" badge unless the user's existing reveal setting says otherwise. `dataSaver` → no thumbnails load until tapped (type icon shown). | Existing privacy prefs apply to new surfaces. |
| DC-13 | Folder navigation is in the route: `Drive: '/drive/:folderId?'`. Browser back = parent history. | Deep links, web back button. |
| DC-14 | The collection kit item model is a union: `{kind: 'favourites'}` \| `{kind: 'clip', clip}`. Shared tile/row/mosaic code takes a thumbnail source and a title, never a `ClipSummary`. | Keeps the uniform look without merging the two features. |

Record DC-1..DC-14 in `docs/DECISIONS.md` in Slice 1.

## 4. Architecture

### `packages/fedi`

- `core/backend.ts`
  - `DriveApi`: add `usage(): Promise<{capacity, usage}>`; `files()` gains `sort?: DriveSort` (sent only when `capabilities.drive_sort === 'supported'`); `moveMany?(fileIds, folderId)` (present only when `drive_move_bulk` is supported).
  - `DriveFoldersApi`: `list(opts: {parentId: string | null} & PageOpts): Promise<Page<DriveFolder>>`; add `show(id): Promise<DriveFolderDetail>` (`{folder, path: DriveFolder[] (root→self), filesCount, foldersCount}`).
  - `ClipSummary`: add `lastClippedAt, createdAt, owner: Account | null, isOwn`.
  - `ClipsApi`: `list(opts: PageOpts): Promise<Page<ClipSummary>>`, `show(id)`; `update` takes the full `{name, isPublic, description}`.
  - `BookmarksApi`: unchanged (already `list/add/remove`).
- `core/models.ts`: `AccountLimits {clipLimit?, noteEachClipsLimit?, driveCapacityMb?}` on the viewer's account (from `i.policies`; absent fields stay absent).
- `core/detect.ts`: keys `drive_sort`, `drive_move_bulk` — default `unknown` for every flavor; raised by probe. Same probe-cache mechanism as `notification_requests` / `like`.
- `core/driveOps.ts` (pure): `runPool(items, worker, {concurrency})` → per-item results; `planFolderDelete(tree)` → depth-first order; `collectMosaic(posts, max=4)` → images in order (skips non-image, keeps `isSensitive`).
- `misskey/drive.ts`, `misskey/clips.ts`, `misskey/favorites.ts`, `misskey/adapt.ts`, `misskey/auth.ts` (no scope changes; B4 logged only).
- Errors (`core/errors.ts`): `NO_FREE_SPACE`, `MAX_FILE_SIZE_EXCEEDED`, `UNALLOWED_FILE_TYPE`, `INAPPROPRIATE`, `INVALID_FILE_NAME`, `HAS_CHILD_FILES_OR_FOLDERS`, `RECURSIVE_NESTING`, `NO_SUCH_PARENT_FOLDER`, `NO_SUCH_FOLDER`, `ALREADY_CLIPPED`, `TOO_MANY_CLIP_NOTES`, `NO_SUCH_CLIP`, rate limit.
