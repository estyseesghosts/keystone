## Did

- `packages/fedi/src/core/backend.ts`: new optional
  `Backend.uploadProfileImage?(kind: ProfileImageKind, file: File):
  Promise<Account>` plus the exported `ProfileImageKind = "avatar" |
  "banner"`. Optional like every capability-gated member; both shipped
  families implement it, so the editor's disabled path is only reachable
  for a backend that truly lacks the endpoint.
- `packages/fedi/src/mastodon/client.ts`: `MastoClient.patchFormData`
  (multipart PATCH; `fetch` sets the boundary, no manual Content-Type)
  next to the existing `postFormData`.
- `packages/fedi/src/mastodon/endpoints.ts`: `updateCredentialImage(
  client, kind, file)` — ONE `FormData` key (`avatar` or `header`),
  `PATCH /api/v1/accounts/update_credentials`, credential-account shape
  check → `errors.shape.updatedProfile` when the body is unusable.
- `packages/fedi/src/mastodon/backend.ts`: `uploadProfileImage` →
  `adaptCredentialAccount`; `guarded()` passes `patchFormData`;
  `updateProfile` now refuses a Drive-shaped `avatarId`/`bannerId` as an
  unknown credential field (`errors.unsupported.profileField`,
  `params.fields`) instead of the old blanket
  `errors.unsupported.avatar` ("not supported on the Mastodon family
  yet"), which would now be false. The retired code is gone from this
  backend's `UnsupportedKey` union.
- `packages/fedi/src/misskey/backend.ts`: `uploadProfileImage` uploads via
  `transport.upload` (`drive/files/create`, root — no `folderId`) and then
  calls `i/update` with `{avatarId}` / `{bannerId}` from the returned
  Drive file id (guarded shape check → `errors.shape.uploadedMedia`).
  `updateProfile` already forwarded the ids and still does.
- `packages/fedi/src/api/client.ts`: facade forwards `patchFormData`
  (the ACTIVE-session Mastodon client is a `MastoClient`).
- `src/components/Profile/pickProfileImage.ts`: images-only picker with an
  explicit `requestMediaLibraryPermissionsAsync` and a typed outcome
  (`picked | cancelled | denied {canAskAgain}`); reuses the composer's
  `assetToFile` and keeps the lazy `expo-image-picker` import.
- `src/components/Profile/ProfileEditorRows.tsx`: `EditorImageRow`
  (preview node, choose/replace button, `Uploading…`, per-row error,
  disabled-with-reason). Reuses `ProfileAvatar` / `ProfileBanner` for
  previews so the picture is the same widget as the profile header.
- `src/screens/ProfileEditor.tsx`: avatar/banner rows are real on both
  families — pick → upload immediately (no save round-trip), local pick
  preview then the server URL, one upload at a time (the other row is
  disabled WITH a reason), denied-permission / cancel / server errors
  rendered on the row, a failed upload rolls the preview back, unsaved
  text fields untouched, and on success the returned account is written
  to the `me` query (`setQueryData`) and the account row invalidated
  (`QueryClientContext`, optional so bare test trees still render).
- Tests: new `packages/fedi/test/profile-images.test.ts`; new
  `ProfileEditor` cases (enable/progress/error/denied/cancel/cache/
  unavailable + mastodon banner); `mastodon-w8-rows` MD6 id-refusal
  updated; six Mastodon stub clients gained `patchFormData`.

## Decided (→ ADR or DECISIONS entry if load-bearing)

- One seam for both images: `uploadProfileImage(kind, file)` rather than
  `updateAvatar`/`updateBanner` or a `File`-carrying `ProfileUpdate`. It
  keeps the family wire (multipart vs Drive id) entirely inside
  `packages/fedi`, makes availability a member-presence check, and returns
  the refreshed `Account` so the UI never guesses the new URL.
- Mastodon `updateProfile` keeps refusing Drive-shaped ids but with the
  accurate "no such field" error. Not a plan reversal; a message/mechanism
  correction that follows §1.8.
- No new `Capabilities` flag: presence of the optional member is the gate
  (the same pattern as `drive`, `lists`, `updateMedia`). Plan §6's
  "every action gated" rule is satisfied by the disabled-with-reason row.
- `errors.unsupported.avatar` is no longer produced. Its message map entry
  in `src/lib/localeErrors.ts` and the locale catalogs are untouched
  (slice forbids catalog edits) — cleanup follow-up, not a blocker.
