## Follow-up (coordinator-verified failures, same tree)

Three tests failed under `pnpm test`. Root causes traced by re-reading the on-disk code (no gate runs — shared tree):

- Failures 1 (`STORE_VERSION - 1 envelopes migrate forward`, sessions.test.ts) and 2 (`a healthy non-empty rewrite keeps the first backup`): NOT implementation bugs — fixture collisions in my own tests. The file-level `internal()` helper computes `id` before the spread (`id: sessionId(ORIGIN, "acc1"), ... ...over`), so `internal({accountId: "acc2"})` keeps `id === "ORIGIN acc1"`, identical to `s`/`a`. `saveSession` upserts by `id` (documented contract, pinned by the pre-existing round-trip test), so the "second" session replaced the first and the remove emptied the envelope. No implementation change can keep both same-id rows without breaking upsert. Fix (tests only, assertions byte-identical): give the fixtures their consistent distinct ids — `internal({id: sessionId(ORIGIN, "acc2"), accountId: "acc2", token: "tok2"})` in both tests. The spec coverage is unchanged (previously vacuous).
- Failure 3 (Composer autosave notice): two layered causes. (a) Implementation gap, fixed in `Composer.tsx` (autosave block only): the timer callback had no throw-guard — `saveDraft` → `listDrafts` → `getItem` can still throw on a hostile store (helpers only guard the write half, per their boolean contracts, which are unchanged). The block is now `try/catch` → throw counts as failed save → notice; recovery still clears it. (b) Test bug: the timer was advanced outside `act()`, so the notice state never flushed to the tree (sibling tests only assert storage, never rendered output — why only this test failed). Fix: `act(() => { jest.advanceTimersByTime(500) })` on both advances, plus a new test pinning the call-site guard (reads of the draft list throw; mount is unaffected; notice appears). Helpers' contracts untouched.
