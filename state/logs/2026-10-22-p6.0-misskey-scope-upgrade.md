# 2026-10-22 — P6.0 Misskey scope upgrade — subagent (deepseek-v4.1-flash)

Branch: `p6.0-misskey-scope-upgrade`
Goal: a Misskey-family 403 `PERMISSION_DENIED` marks the session and
surfaces the same global re-auth/upgrade prompt as Mastodon, without
inventing a scope list (`docs/clickstone.md` §0.8).

Did:

- `packages/fedi/src/misskey/client.ts`: added
  `setPermissionDeniedObserver` / `PermissionDeniedEvent` and reported from
  the module's single error funnel (`translateError`'s `ApiError` throw) and
  the Drive `upload` 403 branch. Authenticated calls only (`session.token`
  empty → no report); an observer that throws is swallowed and the original
  `ApiError` is still thrown unchanged. The setter returns an
  identity-safe disposer.
- `src/state/session/SessionProvider.tsx`: registers the transport observer
  once per provider and forwards to `store.notePermissionDenied(...)`;
  added `useScopeHealth()` (active session, `useSyncExternalStore`).
- `src/state/session/store.ts`:
  - Removed the blanket Misskey short-circuit. `scopeHealth` for a
    non-Mastodon session now returns `needsUpgrade: true`,
    `generation: 'stale-permissions'`, `reason: 'misskey-stale-permissions'`,
    `missingScopes: []` once a denial is recorded; otherwise the previous
    `not-applicable` / `misskey-no-scopes` result. Mastodon's cached-scope
    diff (ADR 0003) is untouched.
  - `notePermissionDenied(id)`: in-memory `Set<string>`, one marker per
    session, idempotent, no-op for unknown ids and Mastodon-family sessions,
    emits so subscribers re-render.
  - Marker lifetime: cleared by `add()` for the same session id (re-auth
    replaces the token), by `remove`, `dropLocal` (401) and
    `signOutEverywhere`.
  - `scopeHealthSnapshot(id)` + a per-session cache cleared in `emit()`, so
    `useSyncExternalStore` gets a stable object reference (`scopeHealth`
    itself stays fresh per call).
- `src/components/ScopeUpgradeBanner.tsx`: the global prompt. Reads
  `useScopeHealth()` for the active session; renders only when
  `needsUpgrade`. Misskey copy: "This sign-in predates a permission
  Keystone now uses." / "Sign in again to grant it. Everything this sign-in
  can already do keeps working." Mastodon copy: "This sign-in is missing
  permissions Keystone uses." / "Sign in again to refresh this account's
  permissions." Action is the existing Login screen with the session origin
  prefilled. No dismiss, no clear, no revoke. The action button only renders
  when `navigationRef.isReady()` — never an inert control.
- `src/Navigation.tsx`: one `<ScopeUpgradeBanner />` in the shell's main
  column (above the stack, below the mobile strip), so it survives every
  screen unmount and covers every route.
- `src/routes.ts` + `src/screens/Login.tsx`: optional
  `Login: {origin?: string}` param; the screen prefills the server field and
  starts on the external form when the origin is not this app's home
  server. No new route. `navigationRef.navigate('Login')` without params
  still works.
- Kept the local `isPermissionError` handlers in Clips/Drive/Following/
  Followers/Lists/Antennas/ProfileEditor/MutesSection untouched; they are
  now secondary explanations behind the global prompt.

Decided (recorded here for the coordinator; no ADR added):

- **Marker persistence: in-memory, not persisted.** A 403 is evidence from
  a request in this process, not durable account state. Persisting it would
  need a storage-version bump and could outlive the condition; a restart
  simply re-observes it on the next refused call. In-memory still satisfies
  the requirement: it lives in the store, so it survives the failing
  screen's unmount and the shell sees it.
- **Prompt surface: shell banner.** The repo had no Mastodon
  `needsUpgrade` UI at all (per `docs/parity-gaps.md` MD5, "the signed-out
  shell IS the re-auth prompt"; `scopeHealth` was session-layer only). The
  smallest honest global surface is therefore a banner reading
  `scopeHealth` for both families. It adds no route, no fake data, no
  session clearing/revocation.
- **Generation value `'stale-permissions'`, reason
  `'misskey-stale-permissions'`.** Rather than lying with Mastodon's
  `granular`, this names the actual condition: Misskey tokens carry a
  permission set chosen at sign-in, not OAuth scopes, and the server never
  returns the token's list. Hence `missingScopes: []` — the prompt never
  names a scope.
- **Any 403 counts (via `isPermissionError`), not only the literal
  `PERMISSION_DENIED` code.** That matches the existing helper the screens
  use (403 or 401+PERMISSION_DENIED). Accepted noise risk: a per-action
  403 (e.g. blocked target) also marks the session until re-auth; the
  alternative (silently missing stale-token 403s) is worse. Only the
  Misskey family is affected.
- **No React Compiler memoisation of `scopeHealth`.** A direct
  `store.scopeHealth(session.id)` inside the banner was memoised across the
  store emit (the component re-rendered but kept the stale object). Fixed
  with `scopeHealthSnapshot` (stable identity until `emit`) + the
  `useSyncExternalStore` hook; `scopeHealth()` itself stays uncached for
  callers/tests.
