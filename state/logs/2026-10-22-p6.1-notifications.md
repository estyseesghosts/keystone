# 2026-10-22 — p6.1 Notifications (Misskey types + Mastodon dismiss) — agent

Branch: `p6.1-notifications`
Goal: clickstone §1.11 — map the Misskey notification types that fell into
`unknown`, give the chat invitation an honest label, and implement Mastodon
`POST /notifications/:id/dismiss` + `/clear` with family/endpoint gating.

Did:

- Core (`packages/fedi/src/core/models.ts`, `core/backend.ts`):
  - `NotificationKind` + `note`, `scheduledNotePosted`,
    `scheduledNotePostFailed`, `exportCompleted`, `roleAssigned`, `login`,
    `createToken`, `test` (each with a doc line naming the wire type).
    `unknown` stays for `chatRoomInvitationReceived` and fork extensions.
  - `NotificationExt` + `roleName`, `exportedEntity`, `exportedFileId`,
    `achievement`, `failedDraftId` (absent = the wire packed none).
  - `NOTIFICATION_FILTER_PRESETS` + `notes` (`['note']`) and `system`
    (scheduled/export/role/achievement/login/createToken/test/app) presets,
    each carrying `family: "misskey"`; new
    `notificationFilterPresets(family)` returns the presets a family can
    actually serve. Preset values are documented as core KINDS that each
    backend translates — never one family's spelling sent to the other.
  - `Backend.dismissNotification?(id)` / `clearNotifications?()` added as
    OPTIONAL members (the notify surface lives on `Backend`, not a separate
    `NotificationsApi` interface — see Decisions).
- Misskey adapter (`packages/fedi/src/misskey/adapt.ts`, `wire.ts`):
  - `MISSKEY_NOTIFICATION_KINDS` (exported) now covers the whole
    `notificationTypes` vocabulary: `note`, `achievementEarned` (the old
    table matched `achievement`, which Misskey never sends — 10 types were
    landing in `unknown`), `scheduledNotePosted`,
    `scheduledNotePostFailed` (+ fork spelling `scheduledNoteFailed`),
    `exportCompleted`, `roleAssigned`, `login`, `createToken`, `test`,
    plus the grouped labels `reaction:grouped`/`renote:grouped`.
  - `systemExtOf` packs role name / export entity+file / achievement /
    kept draft id. `chatRoomInvitationReceived` keeps kind `unknown`.
  - `misskeyNotificationTypes(tokens)` translates preset KINDS to Misskey
    WIRE types (`achievement` → `achievementEarned`; unknown tokens pass
    through verbatim so fork types stay filterable).
  - Wire type `PinetreeNotification` gained the optional per-type fields
    (`role`, `achievement`, `exportedEntity`, `fileId`, `noteDraft`,
    `invitation`).
- Misskey backend: `notifications()` now sends translated include/exclude
  lists and omits the params entirely when empty (previously an empty
  array could be sent — an unfiltered listing).
- Mastodon (`packages/fedi/src/mastodon/{endpoints,backend}.ts`):
  - `dismissNotification(client, id)` → `POST
    /api/v1/notifications/:id/dismiss` with `encodeURIComponent(id)` and no
    body; `clearNotifications(client)` → `POST
    /api/v1/notifications/clear`. Both wired to the backend, both inside
    the `guarded` error boundary so 404/405 arrive as `ApiError`.
  - `notifications()` answers an EMPTY page when a preset's kinds map to
    zero wire types. Without the guard the empty `types[]` was dropped and
    the server returned EVERY notification — a silent lie (this is what a
    `system`-kind filter would have done on Mastodon).
- UI (`src/`):
  - `src/components/Notification/NotificationRow.tsx`: labels for every
    new kind; `chatRoomInvitationReceived` → "chat invitation"; viewer-event
    rows (no wire actor) render no avatar/name instead of an invented
    "Someone"; packed role name / export entity render as a secondary
    caption; optional `onDismiss` renders a labelled, 44dp-ish dismiss
    control only when a handler is passed.
  - `src/screens/Notifications.tsx`: chips from
    `notificationFilterPresets(family)` (fallback to `all` when the
    selected preset is not servable after an account switch), per-row
    dismiss + `Clear all` (confirm `Dialog`) only on the Mastodon family,
    and 404/405 → action hidden + honest caption. Non-absence errors show
    a message beside the list.
  - `src/state/queries/notifications.ts`: `useDismissNotification`,
    `useClearNotifications` — session-keyed, invalidate
    `[sessionId,'notifications']` on success (no local pruning into a lie).
- Tests (35 new, all failing-then-passing against the old mapping/UI):
  - `packages/fedi/test/misskey-notification-types.test.ts` (15): kind
    table incl. both failure spellings, `note`, chat-stays-unknown,

  - `packages/fedi/test/misskey-backend.test.ts` (+1): preset kinds are

  - `packages/fedi/test/mastodon-backend.test.ts` (+4): dismiss/clear call

  - `src/components/Notification/NotificationRow.test.tsx` (+8): labels,

  - `src/screens/NotificationsFilters.test.tsx` (+2): preset ids,

  - `src/screens/NotificationsActions.test.tsx` (5, new): per-row dismiss,

Decided (→ ADR or DECISIONS entry if load-bearing):

- `chatRoomInvitationReceived` stays kind `unknown` (no chat surface exists
  to route into) but gets the label "chat invitation" — the brief's exact
  requirement; the label lives in the row, the kind in the model.
- Additions to `NotificationKind` are ADDITIVE: every new kind is only
  produced by a mapping entry, so no existing consumer changes meaning.
- Dismiss/clear are OPTIONAL methods on `Backend` rather than a new
  `NotificationsApi` sub-module: `notifications()`/`markNotificationsRead()`
  already sit on `Backend`, and a one-method sub-module would be a larger
  refactor than the surface needs. Recorded here; no ADR (narrow, reversible).
- Presets carry core KINDS plus an optional `family` gate; each backend
  translates. This fixed a real bug — the old `achievement` token was sent
  to Misskey verbatim, so that preset could never match.
- Misskey `notifications/flush` exists upstream but is NOT implemented: the
  brief froze Misskey notification behavior ("Misskey keeps its existing
  behavior"). Recorded for a follow-up slice.
- Push/APNs/FCM untouched, no `expo-notifications` dependency added.
