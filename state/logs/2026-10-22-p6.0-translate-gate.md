# 2026-10-22 — p6.0 translation gate — agent (subagent)

Branch: `p6.0-translate-gate`
Goal: Mastodon-family translation capability comes from
`configuration.translation.enabled`, Misskey-family from
`meta.translatorAvailable`; neither family's evidence may decide the other's
flag (clickstone §0.4, audit risk 8).

## Did

- Audited every path that builds or sets `capabilities.translation`:
  - `packages/fedi/src/core/detect.ts` `buildCapabilities` — **the real
    leak.** Both `translatorAvailable` and `translationAdvertised` were
    applied unconditionally, whatever the flavor. Evidence survives on the
    session (`Session.evidence`) and is replayed through
    `backendForSession` / `activeBackend`, so a stored Misskey flag on a
    Mastodon session (or the reverse) could unlock the Translate row and
    auto-translate.
  - `packages/fedi/src/mastodon/instance.ts` `buildFeatures` — already
    family-scoped by construction: the module only speaks the Mastodon
    instance endpoints, and its family union is Mastodon-only. Still fenced
    with a test that an alien `translatorAvailable` field in an instance
    body is ignored.
  - `packages/fedi/src/misskey/translate.ts` `createTranslator` — already
    family-scoped (`family === "mastodon"` uses `translationSupported`;
    Misskey probes `meta`). Fenced with tests (Mastodon never calls
    `meta`; Misskey ignores `translationSupported`).
  - `src/components/Post/PostCard.tsx` (auto-translate
    `translationSource.supported`) and `src/components/Post/menuModel.ts`
    (`translatable`) — read only `backend.capabilities.translation`; they
    are family-agnostic and consult no other flag. No wrong-flag call
    found, so no menu code change; existing menu tests still pin
    supported / unsupported / unknown behavior.
- Fixed `buildCapabilities`: computed `familyOf(flavor)` once and gated
  each evidence flag on its family. `akkoma:machine_translation` stays the
  Akkoma evidence, also scoped to the Mastodon family (that flag only
  arrives in `pleroma.metadata.features`). An undetected flavor
  (`familyOf` → null) ignores every translation flag, so unknown stays
  unknown and unlocks nothing.
- Added regression tests:
  - `packages/fedi/test/detect.test.ts`: one fence per family plus the
    direct cases and the undetected-flavor case; conflicting pairs prove
    the matching family's flag wins and the alien one is ignored.
  - `packages/fedi/test/session-evidence.test.ts`: the real seam —
    stored cross-family evidence → `backendForSession` leaves `translation`
    at `unknown`; matching evidence still decides.
  - `packages/fedi/test/mastodon-instance.test.ts`: v2 and v1
    `configuration.translation.enabled` true/false → supported/unsupported;
    alien `translatorAvailable` in an instance body → unknown.
  - `packages/fedi/test/misskey-translate.test.ts`: Misskey probes `meta`
    and ignores `translationSupported`; Mastodon uses the table and never
    calls `meta`.

## Decided (→ ADR or DECISIONS entry if load-bearing)

- Evidence of the wrong family is ignored, never applied, and an
  undetected flavor ignores all translation evidence. This is the
  conservative reading of AGENTS §6 ("unmet capability must not unlock
  UI"); behavior for matching-family evidence is unchanged, so no ADR —
  this is a bug fix under the existing capability rule.
