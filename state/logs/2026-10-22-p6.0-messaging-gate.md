Decided (→ DECISIONS/ADR only if the owner promotes them):

- `direct_messages: "unsupported"` is a CLIENT gate, not a server fact.
  Both families have DMs/chat serverside (Mastodon `/api/v1/conversations`,
  Misskey chat), so the reason string never blames the server. The
  capability doc comment says Wave 2 slices 2.1/2.2 flip it per flavor in
  the slice that ships the surface. This is the one deliberately
  client-shaped entry in `FLAVOR_FEATURES`; recorded in the log rather
  than ADR because it reverses no architecture and the plan (§0.9)
  explicitly asks for `messaging: unsupported` with a reason.
- `chats` stays the Misskey-family server feature (unchanged values; test
  pins `mastodon: unsupported`, `misskey: unknown`) so Wave 2.2 can consume
  it without a second meaning.
- Surface choice: the AccountMenu, not Settings and not the sidebar.
  Settings would duplicate the gate in a second tree; the sidebar's
  capability-gated stack entries render nothing when unsupported and have
  no reason affordance. The AccountMenu is the navigation surface where a
  messaging destination would live, already renders disabled rows with a
  reason (`Current account`), and is reachable on both layouts.
- No `Messages` route was added. A route to a "not implemented" screen
  would ship a dead end; the entry is the discoverable signal instead.
- Handler seam: `handlers.user.onMessage?: (post) => …` added so the gate
  has an enable path. Nothing sets it in this slice; it is model API, not
  a shipped control.
