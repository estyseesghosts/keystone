  - `FLAVOR_FEATURES.akkoma`: dropped static `translation: "supported"` →
    unknown default. Probe-backed: the rig Akkoma 403s translate and
    advertises no flag, and the Mastodon transport classifier
    (`mastodon/instance.ts:133,145`) already defaults translation to

    (Mastodon-family `configuration.translation.enabled`).

    server could ever raise translation from "unknown" (proven: fresh
    login stored `pleromaFeatures: []`). Now, on the NodeInfo path, it
    runs the cheap family evidence probe (misskey → `POST /api/meta` for
    `translatorAvailable`; mastodon → instance v2→v1 for
    `pleromaFeatures` + `translationAdvertised`). Non-NodeInfo path also
    collects `translationAdvertised`. New `translationEnabledOf` +
    `fetchInstance` helpers (v2→v1 fallback on 404/405 only, unchanged).
  - `buildCapabilities`: honors `translationAdvertised` (authoritative
    where present); existing `akkoma:machine_translation` raise and
    `translatorAvailable` override untouched.
  - Effect on rig: fresh login evidence carries full `pleromaFeatures`
    (no flag) + `translationAdvertised: null` → `translation: "unknown"` →
    menu Translate row disabled with "This server has no translation

## Decided

- E4 needs no bio-path normalization change: the only collapsing found is
  `htmlToPlainText`'s 3+-blank→2 + trim and `plainFromMfm`'s end-trim —
  both keep paragraph breaks; not load-bearing. (Recorded here, not in
  `docs/DECISIONS.md` — read-only for this workstream.)
- E6 outcome is the probe-backed report + honest gating (static Akkoma
  "supported" → unknown with evidence-raise), not a fake Translate row.
  A translation-capable Akkoma (`akkoma:machine_translation`), Mastodon
  (`configuration.translation.enabled: true`), or Misskey-family
  (`translatorAvailable: true`) server now raises the row; the rig has
  none of the three.
